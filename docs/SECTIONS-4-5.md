# Sections 4 & 5 — results page and observability

## Wiring into your main stack

```ts
const logGroup = new logs.LogGroup(this, 'ProcessorLogs', {
  retention: logs.RetentionDays.ONE_MONTH,
  removalPolicy: RemovalPolicy.DESTROY,
});
const processor = new NodejsFunction(this, 'Processor', {
  entry: 'src/handler.ts', runtime: lambda.Runtime.NODEJS_22_X, logGroup,
});
const api = makeApi(this, 'schema.graphql');      // + your data sources / resolvers
new ResultsSite(this, 'Site', { api, webDir: 'web' });
new Observability(this, 'Obs', {
  processor, logGroup, alarmEmail: this.node.tryGetContext('alarmEmail'),
});
```

`cdk deploy -c alarmEmail=you@example.com`, then click the SNS confirmation email.

## Using the logger in the handler

```ts
const root = createLogger({ service: 'pv4-ingest' });

export const handler = async (event, ctx) => {
  const parsed = parseBody(event);
  // ...
  const log = root.child({ requestId: ctx.awsRequestId, eventId, bib, revision, status });
  // On TransactionCanceledException with ConditionalCheckFailed, set
  // ReturnValuesOnConditionCheckFailure: 'ALL_OLD' on the athlete item to learn the stored revision:
  log.outcome('IGNORED', { storedRevision, reason: storedRevision === revision ? 'DUPLICATE_OR_SAME_REVISION' : 'STALE' });
  log.outcome('ACCEPTED', { previousRevision });
  log.outcome('REJECTED', { errors, deadLetterKey });   // deadLetterKey = where the raw payload went in S3
  log.metric('TransactionConflictRetries', attempts - 1);
};
```

Every outcome line carries `requestId, eventId, bib, revision, status`: that is what makes
one bib traceable. The same line is the CloudWatch metric (EMF), so logs and metrics can't disagree.

## How reviewers see each requirement

Reviewers probably can't log in to your AWS account. So the evidence has to be the code, the
README, and anything you can show live in the interview.

| Requirement | What they can check | Where |
|---|---|---|
| Page queries `events`, choose one | Open the CloudFront URL | submission |
| Shows `results` + `eventStats` | Same page | submission |
| Re-fetch without reload | Page polls every 5 s while the tab is visible; checkbox can turn it off | submission |
| Nothing hardcoded | `config.json` generated by CDK from the API's tokens | `infra/results-site.ts` |
| Structured JSON logs, trace a bib | Sample trace in README + saved Logs Insights query | `src/obs.ts`, `docs-trace.txt` |
| Custom metric | `PV4/Timing` UpdatesAccepted/Ignored/Rejected via EMF | `src/obs.ts` |
| Alarm in CDK | Rejection-rate and processor-error alarms | `infra/observability.ts` |
| It works | Screenshots of dashboard, a trace, and the alarm in ALARM state | README |

### Screenshots to take after deploying (put them in the README)

1. **Results page** after running `dev/demo.ts race`, then `reopen`, waiting for the 5 second poll, showing the REOPENED flag.
2. **Dashboard** (`DashboardUrl` output) after a demo run.
3. **Logs Insights**: saved query *PV4/Trace a bib*, showing ACCEPTED/IGNORED lines with `storedRevision`.
4. **Alarm firing**: send ~40 corrupt updates in a minute, wait ~3 minutes, and screenshot
   `pv4-rejection-rate-high` in ALARM. Then send clean updates and show it returning to OK.
   This proves the alarm works rather than just exists.

```bash
for i in $(seq 1 40); do curl -s -XPOST "$INGEST_URL" -d '{"eventId":"ALARM-TEST","bib":"X","lane":1,"revision":1,"status":"bad","timeMs":1}' >/dev/null; done
```

Wipe the data afterwards (redeploy or truncate), so `updatesRejected` is 0 at handover.

## Cost

Both alarms, both saved queries and the dashboard are inside the CloudWatch free tier
(10 alarms, 3 dashboards). The three custom metrics use the single `Service` dimension, so
they stay within the 10 free custom metrics. `eventId` and `bib` are deliberately *not*
dimensions: each distinct value would be a separately billed metric.
